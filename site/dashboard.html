03 / CAPACITY FRAMEWORK

Booked capacity ≠ expected occupancy

The operational opportunity
Bookings tell us demand.
Attendance tells us utilization.
Expected attendance can help us manage capacity before the class starts.

Attendance becomes a utilization measure when it is linked to the actual capacity of each class session. This lab explores the framework; local session data is the next step.

ILLUSTRATIVE EXAMPLE · ASSUMED VALUES
Class capacity20
Bookings20
Booked capacity100%
Assumed average P(attend)82%
Expected attendance16.4
Expected occupancy82%
Expected attendance = Σ P(attendᵢ)
Expected occupancy = expected attendance / capacity

This example is hypothetical. The 82% assumption is unrelated to the GoalZone attendance rate. It does not justify releasing extra places.

04 / EVIDENCE & LIMITS

What this dataset can support

Source and data quality

    The author-referenced CSV is the analytical source. The normalized Parquet matches all 1,500 records on shared fields. The 15-row CSV is a preview; the Kaggle notebook is a reference. Supplied files remain unchanged.

    Definitions and interpretation

    Attendance rate = attended booking records / all booking records in the selected cohort.

    Non-attendance = recorded outcome 0. Cancellation and confirmed no-show cannot be separated.

    Unavailable: session identifiers, capacity, exact class times, calendar dates, member identifiers, cancellations and waitlists. Actual occupancy and empty places cannot be measured.

    Statistical scope: unadjusted associations. Wilson intervals assume independent booking outcomes; repeated-member dependence cannot be checked. n < 30 is a display caution, not a validation threshold.

    Product scope: public-data exploration. No Optimo model, causal claim or automated overbooking recommendation.

    03 / CO-PREFERENCE RULES

    Which classes share an audience?

    A → B means “among members naming A, how many also name B?” It is not a behavioral sequence.

    Exploratory count cutoff; no significance claim.
    Support = pair members / group participants. Confidence = pair members / antecedent members. Lift = confidence / consequent preference share.
    Lift above 1 suggests positive co-preference in this sample. Favorite lists contain 1–3 choices, which can influence associations. Rules are exploratory and do not prove competition, complementarity or conversion uplift.
    04 / PROGRAMMING HYPOTHESES

    Turn preferences into questions to test

    Class demand is not only volume.
    Member preferences reveal shared interests that can inform programming and cross-sell hypotheses.

    Operational data must establish whether classes actually compete, complement each other or create incremental uptake.

    Programming

    Use popular favorites to prioritize demand checks. Compare stated interest with bookings and attendance before adding sessions.

    Schedule compatibility

    Investigate shared-interest pairs against the actual timetable. Preferences alone cannot establish a collision or an ideal class time.

    Cross-program tests

    Explore class and PT offers for relevant members. Measure incremental uptake with an opt-in test and a comparison group.

    Keep the two laboratory questions distinct

    Dataset A: Which bookings turn into attendance? Dataset B: Which members report participating, and which classes share stated interest? Combine the concepts with local member, booking and session data; do not combine the public datasets as one population.

    05 / EVIDENCE & LIMITS

    Member data quality and interpretation

    Source checks

      Favorite labels are preserved exactly as supplied, including HIT, LesMiles and Kickboxen. They are not automatically mapped to GoalZone categories. Source files remain unchanged.

      What this analysis does not measure

      Participation is reported: attend_group_lesson is a member-level flag, not a dated attendance log.

      Preferences are stated interest: no observed scheduling conflict, class attendance frequency or cross-sell outcome is available.

      Source verified: the author describes simulated membership data for EDA, licensed CC0. These generated profiles do not describe Optimo members or validate real-world behavior.

      Privacy in this view: dates of birth, gender, supplied age, trainer names and source IDs are excluded from the dashboard payload and cohort export.

      Next data: stable member IDs linked to chronological visits and class bookings, session schedules, attendance, capacity, cancellations and timestamped preferences.
